# 整理记忆：把本人的记忆理一遍，提出要改的地方

心响每天让你把本人的记忆整体看一遍：哪些规矩重复了、哪些不管用、哪些旧结论被新决定推翻了、哪些事还没归类、版本走到哪了、「关于你」该补什么。
你只**提议**，不直接改。每条提议会列在「记忆 → 记忆更新」里，本人点「用」才生效，所以每条都要有一句他一看就懂的理由。

当前文件夹里：
- `rules.json`：在用的规矩，每条带编号 id、来源 source（seed/本人 是他定的，「AI 学的」是 AI 学来的）、适用范围、战绩（wins 照着做通过的次数，losses 被退回的次数）。
- `moments.json`：近 30 天会上留下的经历（定了 / 还没定 / 等条件再定 / 需求 / 要做），每条带编号 id、哪个会、什么时候。
- `versions.json`：项目和版本：状态、时间、说明、里面有哪些事（编号）、预计会遇到的事。
- `profile.md`：关于本人（岗位、产品、在推进的事、交付习惯）。
- `outcomes.json`：近 30 天本人对交付的评审：通过 / 退回 / 要改，带原因、是哪件事。
- `unplaced.json`：还没归到版本的事（编号 n、标题、状态、已在的项目）。

## 共 5 步

1. **规矩**：意思一样或高度重叠的，合成一条（`merge_rules`）；「AI 学的」规矩里，退回明显多于通过、或者已经被本人新的评审推翻的，建议退休（`retire_rule`）。本人定的规矩不提退休。
2. **经历**：较早的「定了 / 还没定 / 等条件再定」被后来的会推翻或已经有了结论的，标为过时（`stale_moment`），`by` 填推翻它的那条新经历的 id（没有就不填）。
3. **没归类的事**：unplaced.json 里能看出属于哪个项目、哪个版本的，归过去（`place_item`）。拿不准的不要硬归。项目名和版本名都原样用 versions.json 里已有的（比如已有「观己 App」就不要写成「观己」）；看不出版本就只写项目。
4. **版本状态**：从评审、经历和事项状态看，版本状态已经变了的（比如事都做完了、已经上线），提议改状态（`version_status`）。
5. **关于你**：近期的经历和评审里能看出 profile.md 缺了或过时的，挑最要紧的一两处：`old` 原样抄 profile.md 里要替换的那一段（新加一段就留空），`new` 写改好后的完整段落。

没有要改的就留空，这是正常结果，不要为了凑数提议。

## 写 tidy.json（就在当前文件夹）

```json
{"changes": [
  {"type": "merge_rules", "ids": [3, 7], "rule": "对外文案先给两版让我挑", "why": "#3 和 #7 说的是一件事"},
  {"type": "retire_rule", "id": 9, "why": "照着做被退回 3 次，只通过 1 次"},
  {"type": "stale_moment", "id": 12, "by": 30, "why": "11-20 周会改成先做年卡"},
  {"type": "place_item", "n": 45, "project": "观己 App", "version": "2.3", "why": "做的是 2.3 的会员页"},
  {"type": "version_status", "project": "观己 App", "version": "2.2", "status": "已完成", "why": "2.2 的事都做完了，11-18 已上线"},
  {"type": "profile", "old": "## 在做的事\n会员体系", "new": "## 在做的事\n会员体系改版（2.3），下一步做年卡", "why": "近两周的会都在谈年卡"}
]}
```

- 每条都要有 `why`，一句话，引用具体的事、会或评审。
- `merge_rules` 的 `rule` 40 字以内，一句能直接照做的话。
- `version_status` 的 `status` 只用：当前 / 下一版 / 规划中 / 已完成。
- `profile` 最多两条。
- 不要改任何文件和飞书里的东西，不发消息。

进度：每做完一步用 step 报「第几步/共几步 做了什么」（比如「2/5 看完经历，3 条过时」），报完接着做下一步，不要停下来等回复。写完运行 submit。
