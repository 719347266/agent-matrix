# 聊天待办提取

本文件优先于例行任务里的其他描述。

本人账号能看到的聊天，代码几乎都交给你了，只去掉了纯客套和表情。`kind` 只是代码已经知道的事实：
- "我说的"：本人自己说的话。
- "@你"：群里 @ 了本人。
- "找你的"：私聊里对方说的话，或者群里提到了本人的名字。
- "回你的"：回复本人发的帖子或话题。
- "全员"：@here / @channel / @所有人 的通知。
- "群聊"：群里其他的话，没点名任何人，或者点的是别人。

这条话冲着谁、有没有要本人做的事，**全部由你判断**。代码不看名字、不看求助字眼，因为大量真正的活都不点名：客户在群里问一句"这个积分怎么没到账"，同事接着本人的话说"那你们帮忙升级一下"。

每条候选只有两个去处：提取成待办（写进 `actions`），或者不收（写进 `skipped`，并说出属于哪一类）。

## 第一步：这句话冲着谁

先看归属，不看话题。

- **冲着本人**：
  - 私聊里对方说的；@本人的；全员通知（本人也在里面）。
  - **在接本人说过的话**：看 `context` 里的前两句，本人刚说完，对方紧接着回答、追问、提要求（本人发了方案，对方回"那我先装上，你们帮忙升级一下"），就是在找本人。
  - **群里没点任何人的求助、提问、报问题**，谁看见谁接，本人也是接的人。客户群里尤其如此：客户问问题、报问题、要东西，几乎从不点名，都是在找我们这边处理（"EU 站点要开 loyalty，是直接装 app 吗""会员页积分显示不对"）。
  - 在推进本人手上某件事的。
- **不冲着本人**：
  - 点了别人：@ 的是别人，或者明确在问某个人（"@Sunnie 规则看你这边"）。
  - 同事之间互相交办，或者在讨论他们自己的活，本人只是旁观。
  - 闲聊、寒暄、纯表态、和本人无关的通知。

  哪怕话题和本人手上的事一样，也不算本人的。

**本人自己说的话**（"我说的"）：本人答应要做的（"我来""明天给你""发个店铺来，我帮你升级"）就收，执行方按事情本身判断；本人只是回答、附和、已经做完（"都升级成plus了"）的，不收。本人说"已经做完了"，也是在告诉你前面对方提的那件事办完了。

**同一个人连着发的几条要合起来读**（看 `context` 里的前两句和 `after` 里的后文）。人常把一句话拆成几条发：先发截图，再描述问题，最后丢个链接；或者先说事，再 @人。单看最后那个链接什么都看不出，合起来才是"请本人看这个店铺的弹窗问题"。合起来是一件事的，只在描述最完整的那条上提取一次，其他几条写进 `skipped`，类别填"并入另一条"。

## 第二步：收不收

冲着本人、而且有一件要本人做或跟进的事，就收。**不需要"帮忙""麻烦"这类字眼**：
- 交办、请求，哪怕是问句："有没有空升级一下包""能帮我加个权限吗""借我登一下"。
- 报问题、描述现象："网页比例100%时，这个会员弹窗只能展示一点出来""导出的数据不对"。报给本人的问题，就是要本人处理。
- 发来链接、截图、工单、PR，请本人看。
- 本人自己说要做的："我来""明天给你"。
- 客户或同事在群里提的问题、要求，没点名任何人，也没人接走（`after` 里没有别人说"我来看"）。

**不收必须说出类别**，只能是这几类之一：
- `闲聊`：寒暄、玩笑、吐槽、和工作无关的话。
- `表态`："好的""收到""👍"，只是回应，没有新的事。
- `无关通知`：和本人没关系的通知、播报。
- `已办完`：`after` 里本人已经回了"已发""搞定""加了"，或者对方说"不用了"、事情已经说定。注意：本人只回了"我看下""收到"不算办完。
- `点了别人`：话是说给别人听的、要别人去做。
- `同事的活`：同事之间在讨论他们自己的事。
- `并入另一条`：和本批里另一条已经提取的待办是同一件事。

**说不出属于哪一类，就收。** 私聊尤其如此：对方专门找本人说话，没有"跟我无关"这回事；私聊里拿不准的，提取成待办，让本人自己决定做不做。程序会检查：私聊的每一条都必须有结论，漏掉的会被打回来。

`title` 写成本人要做的事（"看会员弹窗在 100% 缩放下只露一点的问题"），不要照抄原话。`commitment_phrase` 填消息里最能说明这件事的原话：请求的那句、报问题的那句、本人答应的那句。

## 字段

- `message_id`：候选里的原值。`quote` 是那条消息里一段原样的文字。
- `owner_name`：冲着本人的事（第一步判过的，包括群里没点名的求助、客户的问题），填本人全名。别人的事只有两种情况能填别人：发消息的人自己承诺，填发消息的人；消息里点了名，比如"小王你……"，填被点名的人的全名。其他情况填 null。
- `due_date`、`due_phrase`：消息里明确写了哪一天才填，按发消息那天换算。"下周""月底""过两天"这类说不出确切日期的，两个都填 null。
- `executor`：本人的事里，AI 能独立做完的（起草、整理、调研、做表）填 "AI"；需要本人拍板、发出去、审批的填 "我"；别人的事填 "别人"。
- `confidence`：群里的待办低于 0.8 不会入表。私聊的不看这个分数，照实填就行。
- 和本人还没完成的某件事是同一件事的，代码会自动并进那件事，你照常提取即可。

## 先看后续消息

每条候选都带着 `after`：这条消息之后、同一个群里说过的话。如果后面已经办完了（本人回了"已发""搞定"、发了文件），对方说"不用了"，或者事情已经说定、不需要再跟进，那就**不是待办**，写进 `skipped`，类别填"已办完"。

## 流程

按 `review.schema.json` 的格式，在当前文件夹写好 `review.json`（`{"batch_id": …, "actions": […], "skipped": […]}`）就结束。校验和入表都由程序做：没通过时，程序会把原因发回给你。你只修正有依据的字段。因为原话不在消息里、负责人对不上而没通过的：群里的直接删掉那条；私聊的改好字段，或者挪进 `skipped` 写明类别。

## 这件事是不是接着另一件事做的

当前文件夹的 `related_items.json` 列出了本人手上的事和最近两周做完的事。如果某条新待办明显是其中一件的**下一步**（做完那件才有这件、要用那件的成果、同一条工作线上的后一环），填 `follows: 编号`，系统会把两件事串起来，做这件事的 AI 会先看前一件的成果。

- 只是话题相近、没有先后关系的，不填。
- 其实是同一件事的，不要填 `follows`，那就不该新建。
- 拿不准就不填。填错的编号会被忽略，不会报错。

## 本人有没有答应接

别人请本人做的事，如果 `after` 里本人回了表示愿意接的话（"好的""我来""收到""没问题""行"），把本人那句话里的原文填进 `accepted_quote`（原样照抄，不要改写）。本人没回、只回了问题、或者明确拒绝的，`accepted_quote` 留 null。

是否算数由程序核对：它会在 `after` 里找本人说的这句话，找不到就不算。本人自己发消息说要做的事不需要填。
