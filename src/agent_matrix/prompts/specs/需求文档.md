# 需求文档：资深产品经理会怎么写

## 结构
1. 要解决什么问题（或背景）：现在是什么样、哪里不好、谁受影响；这次要做成什么样。
2. 目标和衡量：做完怎么判断有没有用（指标或可观察的变化）。
3. 范围：这次做什么、明确不做什么。
4. 需求：按功能或页面分节。每条规则写成「什么情况下 → 系统怎样」，写全边界情况（没数据、出错、权限不够、次数用完、老用户 / 新用户）。
5. 交互和界面：入口在哪、关键界面上有什么、文案怎么写；有原型或参考就附链接。
6. 验收标准：测试照着就能验的几条。
7. 待确认：没定的事、谁来定、建议怎么定。

## 写法
- 开头两三句话让没参加讨论的人看懂为什么做。
- 规则用编号列表，一条只说一件事；数字、名称、版本从现有文档里查，附链接。
- 和已有功能、已有规则的关系写清楚：沿用、修改还是替换。
- 不写实现细节，除非它决定了产品行为。

## 检查清单
- 会上定下的、提需求的人说过的要求，每一条都写进去了
- 每条规则都写了边界情况
- 有验收标准，测试能照着验
- 用到的现有规则和数字都有出处
- 没有凭空编的规则、数字和例子；拿不准的在「待确认」
- 没参加会的开发和设计读完能动手
