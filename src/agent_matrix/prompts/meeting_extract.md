# 提取会议待办：只收会上真正有人接下的新事

## 要交出什么

当前文件夹的 `review.json`，结构见 `review.schema.json`。`meeting_id`、`transcript_sha256` 只用开头给出的实际值。

**大多数会议没有新待办**：例会同步、信息分享、头脑风暴、澄清概念、闲聊都是。`actions` 为空是正常、正确的结果，不要为了有产出而提取。

## 输入

- `transcript.md`：原始逐字稿，不用飞书 AI 纪要。先读完整份，长稿分段读，最后合并重复项。
- 开头给的没完成事项文件（`open_items.json`）：本人手上还没做完的事，用来认出「同一件事」。
- `related_items.json`：本人手上的事和最近两周做完的事，用来认出「接着哪件事做」。

## 一条待办要同时满足三点

1. **有具体动作**：动词 + 对象，事后能判断做完没做完。
2. **有人承接**：原话里有人接下或被指派，比如「我来」「我去弄」「你负责」「XX 弄一下」「回头发你」。把这几个字原样写进 `commitment_phrase`。
3. **是新的承诺**：已经做完的事，或者「可以考虑」「看看」「研究一下」「要不要」「之后再说」「我再看看」这类话，都不算。

## 不是待办的，放进对应的地方

| 会上说的 | 放进 |
|---|---|
| 已经拍板的结论；条件已经满足的安排（「这部分交给小李做」） | `decisions` |
| 讨论的产品需求：功能、指标、规则 | `requirements` |
| 会卡住某条待办的问题 | `open_questions` |
| 「先放着」「等周五数据出来再定」「下次会再看」 | `waiting` |
| 「我们要……」「后面得……」没人接；有条件、条件还没落实的说法 | 不写 |

不要输出 suggestions。

## 每一条都要有

`text`、`quote`、`timestamp`、`reference`：

- `reference`：逐字稿里一段连续、原样的原文，包含 `quote` 和 `timestamp`。
- `timestamp`：用原文里已有的时间，不要猜。

## actions 的字段

- `title`：动词开头，20 字以内。
- `owner_name`：只有两种情况能填。说话人自己承诺（「我来」），填这句话的说话人；原话点了名（「小王你……」），填被点名的人的全名。只说「你」没点名的，填 null。「说话人 N 用 XX 的设备」不等于 XX 本人在说。代码会核对，对不上就拒收。
- `due_date`、`due_phrase`：会上明确说了才填。`due_phrase` 原样引用日期说法，按会议日期换算；没说就都填 null。
- `direction`：mine（本人要做）、others_to_me（别人答应给本人）、others（和本人无关）、unknown。
- `executor`：本人的事里，整件能由 AI 独立做完的（起草、整理、调研、做表、准备材料）填 "AI"；要本人拍板、对外发送、审批或发布的填 "我"；别人的事填 "别人"。
- `ai_can_prep`：本人要做、但 AI 能先备材料的，填 true。
- `done_when`：做到什么程度算完，30 字以内。
- `confidence`：你对「这确实是一个新承诺」的把握。低于 0.8 不会入表；宁可漏，不要凑。
- `same_as`：其实是没完成事项里某一件的新进展、新要求或同一份交付物，填它的编号；系统会并进那件事，不新建。拿不准不填，代码还会按标题再比一遍。
- `follows`：明显是 `related_items.json` 里某件事的下一步（做完那件才有这件、要用那件的成果、同一条工作线上的后一环），填它的编号，做这件事的 AI 会先看前一件的成果。只是话题相近不填；是同一件事用 `same_as`；拿不准不填，填错会被忽略。

## waiting 的字段

- `text`：等着定的是什么事，20 字以内。
- `wait_for`：在等什么条件，原样概括，比如「周五的投放数据」。
- `due_date`、`due_phrase`：原话里有日期才填，规则同上。
- `quote`、`timestamp`、`reference`：必须是原话。

心响会记住它：日子到了，或者以后的会上又谈到同一个话题，会把当时的原话带回来给本人。

## 交了之后

校验和发布由程序做；没有待办的会，不会发任何消息。没通过时程序会把原因发回来：只改有依据的字段；因为缺承接字眼没通过的，说明它本来就不是待办，删掉这条。
