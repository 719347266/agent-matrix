# 新进来的事：先看上下文，再判断要不要做、谁来做

`items.json` 里是刚进表、还没定谁来做的事。每件事有标题、要做什么、原话、来源、`version`（所在的项目和版本，空表示还没归到版本），以及 `after`：从这件事冒出来到现在，相关的聊天记录（程序已经替你找好）。

`open.json` 里是本人手上还没做完的事（编号 n、标题、状态、所在版本），用来找新事的前后关系。
`versions.json` 里是本人现有的项目和版本（没完成的），用来给还没归版本的新事找归属。

**先看 `after`，再下判断。** 很多事本人已经在对话里办完了，或者对方说不用了，只是现在才被捞起来。觉得 `after` 不够，可以自己用 `lark-cli` 只读地再查，比如搜聊天、读文档。

## 五种判断

- **done（已经办完）**：`after` 里能看到本人已经做了，比如发了文件、回了"已发""搞定"，或者对方确认收到。要在 `evidence` 里写出是哪一句；有交付文件链接的，写进 `url`。
- **skip（不用做）**：不是真的待办，比如只是随口一说、对方说不用了、和别的事重复了、已经过时了。
- **ai（AI 能独立做）**：AI 能独立做完，结果是一份文档或表格，比如起草、整理、调研、汇总、做表、写方案、准备材料。
- **prep（本人做，AI 先备材料）**：得本人来，比如拍板、对外沟通、开会、审批，但 AI 可以先备好材料。
- **me（只能本人做）**：AI 先备材料也帮不上忙。

## 规则

- done 和 skip 必须有依据：done 要写出原话证据，skip 要写清原因。没把握就不要判 done 或 skip。
- 对外发送、提交审批、付款、删除、发布：不能判成 ai，最多判 prep。
- 拿不准该谁做时，判 prep。
- `reason` 用 30 字以内写清为什么，写给本人看。

## 顺带补上前后关系（要做的事才补：ai / prep / me）

- `before`：新事开始前要先做完的事，写 `open.json` 里的编号。
- `after`：新事做完后接着要做的事，写编号。
- `version`：新事的 `version` 为空、又明显属于 `versions.json` 里某个版本时，写 `{"project": "项目名", "version": "版本名"}`（必须原样用里面的名字）；看不出就不写。
- `expected`：新事所在版本（或你刚给它归的版本）预计还会遇到、但表里还没有的事，比如上线前验收、配套的文档或通知。每条写 `title`（一句话）、`why`（为什么会遇到），知道日子就写 `due`（如 `2026-11-28`）。`version` 为空的事不用写。
- 只写看得出来的关系，比如标题或原话里提到了、明显是同一件事的上一步或下一步。没把握就不写，三项都可以省略。
- 每项最多 3 个。不要写新事自己的编号。

## 输出格式（triage.json）

```json
[{"n": 47, "decision": "done", "reason": "本人已在群里发了审核材料", "evidence": "[11-17 15:02 本人] 材料已提交，电话也认证了"},
 {"n": 49, "decision": "ai", "reason": "按现有岗位要求起草 JD，AI 能独立完成", "before": [31], "after": [52], "version": {"project": "招聘", "version": "12 月"},
  "expected": [{"title": "JD 发布前请用人部门确认", "why": "岗位要求还没定稿", "due": "2026-11-28"}]},
 {"n": 50, "decision": "skip", "reason": "对方说这周先不招了"}]
```

只写 `triage.json`，不改任何东西。
